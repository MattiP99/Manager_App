- **`DetailModal.tsx` è diventato il pattern di navigazione centrale dell'app**, con un prop `variant?: 'center' | 'sheet' | 'side'` (prima solo un booleano `sheet`, poi generalizzato quando è servito un terzo tipo):
  - `'center'` (default, invariato) — card centrata, dissolvenza, comportamento originale di Blocco B.
  - `'sheet'` — foglio che sale dal bordo inferiore (`animationType="slide"`), **80%** dell'altezza schermo (partito da 75%, alzato su richiesta), larghezza piena su mobile/web stretto e **doppia del modale standard (840px)** su web ampio (`isWideLayout`, stessa soglia 820px del resto dell'app). Usato per ogni "drill-down" di primo/secondo livello: aggiungi/modifica nota, riepilogo metrica Pagamenti, dettaglio cliente, riepilogo giornata Calendario (Lavoro e Francesca).
  - `'side'` — pannello laterale ancorato a destra, introdotto per Pagamenti e riusato identico per Calendario: uno **scorrimento orizzontale animato con `Animated` di React Native** (nessuna libreria di animazione in questo progetto — `useNativeDriver: true`, 320ms), non la semplice dissolvenza di `Modal` che da sola non mostra alcun movimento (bug segnalato dall'utente e corretto). Il Modal nativo smonterebbe subito quando `visible` diventa false, prima che l'animazione di uscita possa scorrere — risolto tenendo un secondo stato locale (`mounted`) che si aggiorna solo a fine animazione (`Animated.timing(...).start(() => setMounted(false))`). Altezza dimezzata (50%) su mobile/web stretto su richiesta esplicita (era piena altezza), rimasta piena su web ampio (mai chiesto di cambiarla lì). Usato per le azioni di terzo livello innescate da dentro un foglio già aperto: aggiungi giornata lavorata/pagamento (dal dettaglio cliente in Pagamenti), aggiungi giornata/evento (dal riepilogo giornata in Calendario) — stessa distinzione visiva per non impilare due fogli identici indistinguibili.

## Environment quirks specific to this project — save yourself the rediscovery

These bit multiple tasks across both blocks before being understood. **Include them in every implementer/reviewer dispatch that touches routes or does a `tsc --noEmit` check:**

1. **`.expo/types/router.d.ts` (gitignored) only fully regenerates after Metro completes a REAL bundle pass** — triggered by an actual HTTP request to the running dev server, not just the server starting up ("Waiting on http://..."). A `tsc --noEmit` run against a stale/partial version of this file produces spurious `router.replace('/')`-style errors, or (worse, seen once) a corrupted file with bogus route entries from an interrupted earlier run. **Correct verification sequence:** `npx expo start --web --port <N> &` in background → wait for "Waiting on http://..." in its log → `curl -s -o /dev/null http://localhost:<N>/` to force a real bundle → wait a few seconds → then run `tsc --noEmit` → then kill the background server (`netstat -ano | grep :<N>` then `taskkill //F //PID <pid>` on this Windows machine). Never just start-and-immediately-kill.
2. **Numeric Postgres columns (`numeric(10,2)` etc.) return as genuine JS `number` via supabase-js in this project** — empirically verified with a live throwaway script against the real database (see Clienti+Pagamenti plan's ledger, now deleted — the finding itself is what matters: don't add defensive `Number()`/`parseFloat()` coercion around Supabase query results "just in case," it's unnecessary here even though PostgREST folklore suggests otherwise for some setups).
3. **Any new Postgres view MUST declare `with (security_invoker = true)` explicitly.** Without it, a view runs with the view owner's (migration role's) privileges for RLS purposes, not the querying user — silently bypasses household isolation. This exact bug class caused a real incident in the Fondamenta block (`household_members` self-referential RLS recursion, fixed via a `SECURITY DEFINER` helper in migration `0002`) and was correctly avoided from the start in Clienti+Pagamenti's `work_session_status` view (migration `0004`).
4. **The established RLS pattern for new household-scoped tables:** `is_household_member(household_id)` (the helper function from migration `0002`) used as both `USING` and `WITH CHECK` in a single `for all` policy per table — no per-table RPC needed (that pattern is reserved for the household creation/join flow specifically, which needed atomicity + not exposing invite codes). Copy this template for every new table in future blocks (calendar events, expenses, notes).
5. **This execution environment has no interactive/headless browser tooling** (no Playwright/Puppeteer, nothing that can click through a UI). Established, repeatedly-applied standard: task/final reviews substitute careful hand-tracing of the actual diffed code (navigation param names matching end-to-end, conditional logic not inverted, correct field usage) for a literal browser click-through, and this has been treated as sufficient rather than a blocking gap — but real bugs have still been caught this way (see below), so don't use this as an excuse to skip careful review.
6. **List queries need an explicit secondary `.order()` tiebreak** — Postgres doesn't guarantee row order among ties on a single sort column (`date`, `name`, etc.). This has already had to be fixed twice (once in Fondamenta for household selection, once in Clienti+Pagamenti's final review for session/payment/client lists) — get it right from the start in new queries: `.order(primaryColumn).order('created_at', { ascending: false })` (or `.order('id')` when there's no `created_at` to lean on).
7. **`src/lib/database.types.ts` must be regenerated after every schema change**: `export SUPABASE_ACCESS_TOKEN=$(grep SUPABASE_ACCESS_TOKEN .env | cut -d '=' -f2)` then `npx supabase gen types typescript --project-id qivxrbhbffwqqmaadpnl > src/lib/database.types.ts`. Use the typed client (`createClient<Database>`) — casts like `as WorkSessionStatus[]` are fine when narrowly scoped to a known codegen quirk (generated/view columns marked nullable even when the schema guarantees they're present) but were specifically investigated field-by-field in two separate reviews before being accepted as safe, not rubber-stamped.
8. **The root layout's `<Slot />`-without-`Stack` (see item above about explicit back buttons) also means screen-local `useState` is lost on navigate-away-and-back** — there's no navigator keeping the previous screen instance alive, so any in-memory UI state on a tab screen resets to its initial value the moment you leave and return. Found in the Calendario Lavoro final review: `CalendarView`'s view-mode/anchor-date state resets to today's week after visiting `/day/[date]` and pressing back. Accepted as a known limitation, not fixed (a real fix means moving that state into URL search params) — the same latent behavior already existed in `pagamenti.tsx`'s period filter before this block. Note it so a future block doesn't "discover" it again.
9. **This project's spec has been wrong about an Expo SDK API's exact surface at least once — always verify live docs, never trust the spec's own claims about a library, even one the spec names specifically.** The spec's §"Cifratura note-password" claimed "PBKDF2 via `expo-crypto`" — `expo-crypto` (SDK 57) has native AES-256-GCM encrypt/decrypt and secure random, but genuinely no PBKDF2/key-derivation function at all. Caught by fetching the live docs during brainstorming (`https://docs.expo.dev/versions/v57.0.0/sdk/crypto/`) before writing the plan, not discovered mid-implementation. Fixed by adding `@noble/hashes` (pure JS, zero deps) for just the PBKDF2 step, feeding its output into `expo-crypto`'s native AES via `AESEncryptionKey.import(bytes)`. Also relevant if any future block touches cryptography or another platform-native module the spec makes assumptions about: `expo-secure-store` has no web support at all (needs the same `Platform.OS === 'web'` fallback pattern as `src/lib/supabase.ts`'s session storage), and passing a plain string to `expo-crypto`'s `aesEncryptAsync` silently requires pre-base64-encoding via `btoa` — which breaks on Italian accented characters (à/è/ì/ò/ù). Always pass `Uint8Array` (via `TextEncoder`), never a string, to sidestep this entirely.
10. **Know exactly which `.env*` file holds which secret before dispatching a task that needs one — this project has two, and mixing them up wastes a whole implementer round-trip.** `.env` (repo root) has `SUPABASE_ACCESS_TOKEN` (CLI/migrations) and the `EXPO_PUBLIC_*` client keys. `.env.test` has separate test-only credentials including `SUPABASE_SERVICE_ROLE_KEY` — that's what `tests/rls/helpers.ts`'s `adminClient` uses, not `.env`. A Note-block Task 1 dispatch wrongly assumed a service-role key lived in `.env` and the implementer correctly refused to work around it with a bulk `auth.users` read rather than improvise against production — good judgment, but it cost a full resume round-trip. Also: an implementer confirming a `.env.test` variable *name* once accidentally echoed an actual *value* into its own transcript while doing so (never into any committed file — independently verified) — when a dispatch needs to reference `.env.test`, explicitly instruct greping for variable NAMES only (`grep -o '^VAR_NAME='`), never the full line.
11. **The RLS integration test suite is now large enough to trip Supabase Auth's own `signInWithPassword` rate limit when run repeatedly in quick succession** — even with `npm run test:rls`'s `--runInBand`, 5+ test files each signing in multiple users back-to-back can produce `AuthApiError: Request rate limit reached` on essentially random files, worse the more you re-run the full suite in a short window. Not a code defect — don't chase it as one. If you need to re-verify a specific new test file, run it in isolation (`npx jest tests/rls/<file>.test.ts --runInBand`) rather than re-hammering the full suite repeatedly; trust a single clean full-suite run (your own or the implementer's, with real pasted output) rather than needing to reproduce it multiple times.
12. **To check real production data during a bug investigation (not just RLS test users), use the service-role key from `.env.test` in a one-off Node script — the same admin client the RLS tests already use.** Confirmed safe and effective 2026-09-23: a user-reported "payment didn't reduce the balance" bug was resolved by querying `work_sessions`/`payments` directly for the real client, which proved the data was already correct — turning what could have been a long guess-and-check debugging session into a 2-minute confirmation. Same secret-handling rule as item 10 applies: read values to use them (this project's anon key/URL are meant to be public anyway, per `LEARNING.md`), never echo a secret value into your own output gratuitously.

## Real bugs that were actually caught this way (evidence the process works, don't skip steps to save time)

- RLS infinite recursion in `household_members`'s own SELECT policy (Fondamenta) — found by running the RLS integration tests for real, not by reading the SQL.
- A "fix" that silently broke mobile session persistence by replacing `AsyncStorage` with a no-op storage adapter on native (Fondamenta) — caught by the controller reading the diff directly instead of trusting a "DONE_WITH_CONCERNS" self-report.
- A spurious redirect bug from misreading React Query's `isLoading` on a disabled query (Fondamenta final review).
- Two genuine money-correctness bugs in `dateRangeForPeriod` — a month-end date rollover silently dropping up to 3 days from period totals, and UTC-vs-local date computation misdating anything logged just after midnight (Clienti+Pagamenti final review) — both in the one function the plan explicitly required to be a tested pure function, which nonetheless shipped two helper functions with zero tests until the final review caught it.
- Weak RLS test assertions that would have passed even with a broken policy (a placeholder client_id causing an FK failure instead of proving RLS was the actual blocker; an unchecked setup insert that could silently produce zero rows and make an isolation check trivially pass) — caught in task-level review, not by the tests' own green checkmarks.
- A reminder-ownership split (Calendario familiare, final whole-branch review) — the per-occurrence-edit/skip mutation (Task 5) and the periodic recurring-template sweep (Task 6) each scheduled/cancelled local notifications under their own key (`event:<id>` vs `template:<id>`) with neither owning the full picture: "Salta solo oggi" left a stale reminder still firing, and "Modifica solo questo giorno" produced a duplicate reminder. Exactly the class of bug a task-scoped review structurally cannot see — Task 5 and Task 6 were each individually correct in isolation, and their per-task reviews were passed cleanly. Only the final whole-branch review, diffing both tasks together, caught it. Fixed by making the sweep defer to any existing override row for a date (cancel its own `template:` reminder and skip) rather than scheduling unconditionally.
- A month-context drop between a screen's own state and its add-form default (Spese mensili, final whole-branch review) — `spese.tsx`'s month navigator (`anchorDate`) and `add-expense.tsx`'s date field (defaulting to today) were each individually correct per their own task's spec, but the "+" button never passed `anchorDate` through, so adding an expense while browsing a past/future month silently dated it to today and made it vanish from the month being viewed. Same bug *shape* as the reminder-ownership split above — two individually-correct tasks whose seam only a whole-diff review can see — but this time on a UI/UX correctness axis instead of a notification-scheduling one. Fixed by passing `date: anchorDate` through the route params, restoring the `params: {date}` convention already used by every other add-screen in the app (`family-day→add-family-event`, `day→add-work-session`) that this block's screen alone had missed.
- A money-parsing gap that would have shipped a third money-correctness bug in this project if the final review hadn't caught it (Spese mensili, final whole-branch review) — `parseFloat(amount.replace(',', '.'))` only replaces the FIRST comma, so an Italian thousand-separator amount like `"1.234,56"` silently became the string `"1.234.56"` and `parseFloat` returned `1.234` with no error, ready to be written straight into a `numeric(10,2)` column. Fixed with a regex pre-check (`^\d+([.,]\d{1,2})?$`) that rejects any thousand-separator shape before parsing, rather than trying to parse-then-validate the result.
- A layout-flex bug on the exact seam between two tasks that each looked correct alone (Blocco B Piano 2, final whole-branch review) — Task 4 restyled `CalendarView`'s `dayCell` and deliberately removed `overflow: 'hidden'` (so the new two-zone content wouldn't get clipped); Task 5 built the two-zone Mattina/Pomeriggio layout with `flex: 1` on both zones, which in React Native means `flexGrow:1, flexShrink:1, flexBasis:0` — an exactly equal 50/50 height split regardless of actual content. Combined, a day with entries only in one zone (the common case: `splitByHalfDay` routes every no-time entry to morning, and historical entries often have no time) rendered its overflow chips spilling past the zone/card boundary instead of being clipped OR the zone growing to fit. Each task's own review passed cleanly — task-scoped review structurally cannot see a sizing policy set by one task colliding with a content policy set by another. Fixed by changing both `halves`/`half` styles from `flex: 1` to `flexGrow: 1, flexBasis: 'auto'` (content-driven height) with a `minHeight: 20` on the empty-zone case to keep its tint band visible. **General lesson for any future RN layout work in this project:** `flex: 1` forces equal-share sibling sizing; `flexGrow: 1, flexBasis: 'auto'` lets siblings size to their own content first and only share leftover space.
- A non-shrinking header that could make an entire list unreachable, again a seam invisible to task-scoped review (Blocco B Piano 3, final whole-branch review) — Task 2 gave the new `PressableCard` shell generous padding (`Spacing.lg` + shadow), Task 4 stacked 4 of them plus a title and period-toggle row as non-scrolling siblings (`flexShrink` defaults to 0 in RN) above a `FlatList{flex:1}` inside a plain `View` — no page-level `ScrollView` anywhere. On a short viewport (phone landscape, a small browser window) that ~460px fixed header could squeeze the client list to near-zero height with **no way to scroll down to it at all**, since the container itself doesn't scroll. Each task was individually correct — Task 2's padding was fine in isolation, Task 4's stacking was fine in isolation. Fixed by moving the header content into the `FlatList`'s own `ListHeaderComponent`, making the whole screen (header + client cards) one single scrollable region instead of a fixed block above a separately-constrained list. Also caught in the same review: the period selected on the Pagamenti screen was silently dropped from the UI on the drill-down screen it links to — the *data* traveled correctly through the route params (verified independently, not assumed), but nothing rendered it, so a user drilling into "Dovuto" while viewing "Settimana" saw numbers indistinguishable from the all-time view. A one-line `period`-validation guard was folded into the same fix, since the two touched the same file and the display fix needed a trustworthy value to render.
- The most serious bug this project has shipped a fix for (Note, final whole-branch review, reviewed on opus specifically because this code has zero automated test coverage) — a stale cached encryption key from a different household/session was silently treated as proof "this Password section is unlocked." Task 4 built the key cache as one device-global, unverified slot; Task 6 adopted "a key exists locally" as its unlock predicate; Task 7 inherited that predicate for its own encrypt/decrypt calls. Each task was individually correct and passed its own review. Composed together, reachable via the app's own shipped sign-out button: sign out, sign in as a member of a different household, open that household's never-configured Password section — the old key passes a length check, the setup prompt never shows, and any note added gets encrypted under an orphan key nothing can ever decrypt (by design, no server-side recovery exists for this feature). Fixed with a `loadVerifiedKey()` function that decrypts the section's own stored "canary" value and checks it against the expected plaintext before ever treating a cached key as valid — AES-GCM's authentication tag makes a wrong key fail loudly, so this is a cheap, reliable check. This is the reminder-ownership-split bug's sibling: two-plus individually-correct tasks whose *shared assumption* (not their individual logic) was wrong, invisible to any single task's review, visible only reading the whole diff fresh.

**Takeaway for whoever picks this up next:** independently re-verify `tsc`/test claims yourself rather than trusting implementer self-reports at face value — this has caught real problems on both blocks so far, not hypothetically.
